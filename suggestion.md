# FileShare — Project Analysis & Upgrade Suggestions

> Generated by reviewing the codebase on **14 Nov 2026**. This document covers (1) the two problems you reported
> (multi-file upload errors, slow/error-prone 5 GB uploads), (2) root causes found in the code, and (3) a full
> upgrade roadmap for the project.

---

## 1. Executive Summary

FileShare is a Next.js 16 (App Router) file-sharing app. It uses:

- **Cloudflare R2** (S3-compatible) as object storage, with presigned upload/download URLs.
- **Supabase** (Postgres + Auth) as the database and authentication layer.
- **Upstash Redis** for rate limiting.
- **react-dropzone**, **JSZip** (folder zipping), **bcryptjs** (password hashing), **zod** (request validation).
- **Resend** (presumably for transactional email), **shadcn/base-ui** UI components.

The architecture is good: uploads go **directly browser → R2** via presigned URLs (never through your server),
multipart uploads are implemented for files > 50 MB, and downloads are redirects to signed R2 URLs. The main
problems are in **configuration of rate limits**, **client-side concurrency / resumability**, and **presigned URL
lifetimes**.

### Top actions (do these first)
| # | Action | Fixes |
|---|--------|-------|
| 1 | Make upload rate limits per-user/per-session generous and per-*attempt*, not per-file | multi-file errors |
| 2 | Increase part-level concurrency and generate part URLs lazily | slow 5 GB uploads |
| 3 | Add resumability (persist upload session so a refresh/retry resumes) | 5 GB errors |
| 4 | Extend download URL lifetime / stream large downloads | 5 GB download errors |
| 5 | Make rate-limit failures visible & user-friendly | confusing "error" toasts |

## 2. Issue A — "Uploading more than 1 file tells an error"

### What the code does today
When you select several files, `handleUploadAll()` in `src/components/UploadZone.tsx` uploads them in batches of
3 (`CONCURRENCY = 3`). **Each file is treated as an independent upload** and consumes its own API calls and a
separate row in the `files` table. Only afterwards are the file tokens grouped into a "collection".

### Root causes (ranked by likelihood)

#### A1. Upload rate limits are counted per file, and are low
In `src/lib/rate-limit.ts`:

```ts
export const guestUploadLimit = makeLimiter("guest_upload", 50, "1 h");
export const authUploadLimit = makeLimiter("auth_upload", 50, "1 h");
export const apiLimit = makeLimiter("api", 200, "1 m");
```

Every upload initiation calls `guestUploadLimit`/`authUploadLimit` **once per file**. So uploading a folder of
60 files in an hour exhausts the 50/hour limit → the last 10 files fail with **429 "Upload limit reached. Try
again later."**. Anyone actively testing or bulk-uploading hits this quickly. This is the most common reason
"more than one file" fails.

#### A2. Global API limit shared across all actions
`apiLimit` is 200 requests/min per IP and is checked on *every* route (upload, download, collections, etc.).
Multi-file uploads also trigger: presigned/initiate + confirm/complete (2 per file) + collection creation + per
file collection-link calls. Heavy use (or shared NAT IPs) can trip this and return "Too many requests." on some
files while others succeed.

#### A3. Multipart initiate generates *all* part URLs in one request
For every file > 50 MB, `POST /api/upload/multipart/initiate` builds the **full list of presigned part URLs up
front** with `Promise.all(...)` (see `src/app/api/upload/multipart/initiate/route.ts`). For a 5 GB file that is
100 URLs generated in a single request. If any single signing call hiccups, the whole initiation fails and the
file errors out; it also makes the response large and slow.

#### A4. No graceful handling / messaging for partial batch failures
`handleUploadAll` uses `Promise.allSettled` and just counts successes/failures. When ONE file in a batch fails
(e.g. rate limit), the whole batch still completes, but the UI shows "1 item failed" with no actionable detail,
and retrying can repeatedly fail for the same quota reason.

### Recommended fixes for Issue A

**A1 — Move upload limits to a per-user daily *byte* budget (or at least raise them).**
File-based sharing apps should limit *bytes stored* or *uploads per day*, not per file initiation. Minimal change
in `src/lib/rate-limit.ts`:

```ts
// Better: keep per-user limits but make them generous and daily
export const guestUploadLimit = makeLimiter("guest_upload", 200, "24 h");
export const authUploadLimit = makeLimiter("auth_upload", 1000, "24 h");
```

Even better, enforce a per-user **storage quota** in the database (sum of `file_size` for active files) and reject
uploads that exceed it. This is more correct than request counting.

**A2 — Lower the blast radius of the global API limit.**
Raise `apiLimit` (e.g. 600/min) and/or exempt long-running/background calls. Most importantly, **stop counting
per-file sub-calls as separate "uploads"** — deduplicate the per-file collection-link calls (see A5).

**A3 — Generate part URLs lazily.**
Do not pre-build 100 URLs. Have the initiate endpoint return just `{ uploadId, chunkSize, token }` and add a small
endpoint `POST /api/upload/multipart/part-url` that signs one part URL on demand. The client then requests a URL
only when it is about to upload that part. This removes the fragile `Promise.all` of N signings and keeps the
response small.

**A4 — Make errors actionable.**
Expose the HTTP status/`error` string from the failed per-file request and show it in the file row (e.g. "Rate
limit reached — try again in 1h"). Add a per-file "Retry" button instead of only a global one.

**A5 — Do not double-link files to collections.**
In `uploadSingle()` you already add the file to `defaultCollectionId`; then `handleUploadAll()` adds the same tokens
to a (possibly different) "today" collection. Pick one path. If the user is already uploading into a collection,
skip the auto-grouping step entirely.

## 3. Issue B — "5 GB upload is slow and sometimes throws an error"

### What the code does today
Files > 50 MB take the multipart path in `UploadZone.tsx`:
- `initiate` creates an R2 multipart session and returns **all** part URLs (50 MB chunks).
- Parts are uploaded with **concurrency = 4** (`CONCURRENCY = 4`), each part via `XMLHttpRequest` PUT.
- Each part retries up to **3 times** with fixed 2 s / 4 s backoff.
- Presigned part URLs are valid for **4 hours**.
- On success, `complete` finalizes.

### Root causes for slowness/errors

#### B1. Concurrency of 4 is too low for large files
A 5 GB file = 100 chunks of 50 MB. With 4 parallel uploads you are effectively limited to 4 simultaneous in-flight
PUTs. On high-bandwidth connections this underutilizes the link; on long round-trip connections (mobile, VPN) the
throughput is dominated by round-trip time, so higher concurrency (8–12) dramatically shortens the total time.

#### B2. Fixed 50 MB chunk size + fixed concurrency ignore the connection
A 50 MB chunk on a slow connection is large (each failed retry means re-uploading 50 MB). There is no adaptation to
measured throughput.

#### B3. All part URLs are generated up front (same as A3)
The `Promise.all` of ~100 signings in `initiate` is slow, can fail wholesale, and produces a big response.

#### B4. No resumability — a refresh/error means starting over
Multipart upload state (uploadId, completed parts) lives only in component memory. If the page reloads, a tab is
closed, or an error escapes, the **entire 5 GB upload restarts from zero**. R2 does keep the session until you
abort, but the app never resumes it.

#### B5. Download side: 15-minute presigned download URL can expire mid-download
`src/app/api/download/[token]/route.ts` signs GET URLs valid for `900` seconds (15 min) and the share page redirects
the browser to it. Downloading a 5 GB file at, say, 6 MB/s takes ~14 min — reliably near the edge, and on slower
connections the URL expires **before the download finishes** → the download errors out. This is very likely a big
part of the "5 GB sometimes throws an error" symptom (on the receiving side).

#### B6. Aggressive aborts on any part failure
In the multipart loop, if any part exhausts retries, the client calls the abort endpoint, discarding progress for
all other parts.

### Recommended fixes for Issue B

**B1 — Raise and adapt concurrency.**
Use a higher, configurable concurrency (e.g. 8) or make it adaptive: start with 8 and increase to 12–16 if the
per-part transfer stays fast, decrease on errors.

**B2 — Adaptive chunk size.**
Keep parts between 5 MB and 50 MB; you can choose a smaller chunk (e.g. 10 MB) for slow connections so failures
cost less to retry, and 50 MB for fast ones.

**B3 — Lazy part URL generation (same as A3).**
Add `POST /api/upload/multipart/part-url` that signs one URL for a given part number. The client asks for it right
before uploading that part. This removes the giant `Promise.all`.

**B4 — Resumability (biggest win for 5 GB).**
Persist the upload session so a retry resumes instead of restarting:

- Server: keep `uploadId` and a list of completed part numbers in the `files` row (or a small `upload_sessions`
  table) at initiate time.
- Client: store `{ storageKey, uploadId, chunkSize, totalParts, completedParts[] }` in `localStorage`/IndexedDB
  keyed by a client-generated upload id.
- On (re)start, query `GET /api/upload/multipart/status` → skip already-completed parts, continue the rest.
- Refresh the `complete` call only after all parts are actually uploaded.

**B5 — Fix the download-side expiry.**
Options:
- Increase the presigned GET URL lifetime for large files (e.g. scale with size: `expiresIn = max(900, fileSize / expectedBandwidth)`), **or**
- Stream downloads through your server (or a signed route) so the URL is obtained per-chunk and never expires, **or**
- For very large files, present a real "download" that uses a **range-enabled** signed URL and refresh the signature
  if it is about to expire (more advanced).

**B6 — Don't abort the whole upload on one part failure.**
Only abort if the user explicitly cancels. Let other parts complete; on retry, resume from the last good part.

## 4. Security Review

| Area | Current state | Recommendation |
|------|---------------|----------------|
| Upload auth | Uploads allowed for guests and users; only size/type validated | Add per-user storage quota; consider a session/IP cap |
| File type validation | `validateFileType` is allowlist-based (good) | Also validate on the **server** with magic bytes (not just MIME header) for security |
| Path traversal | `sanitizeFileName` strips `/ \` etc. (good) | Ensure storage keys never embed user-controlled names (they use UUID — good) |
| Presigned URL scope | Upload PUT signed for bucket+key only (good) | Keep `ContentType` out of signed headers to avoid mismatch (multipart path already does this) |
| Secrets | `R2_*`, `SUPABASE_SERVICE_ROLE_KEY`, Upstash keys in env | Ensure they are in `.env.local`/platform and never committed; add `.env*.local` to gitignore |
| Download abuse | `downloadLimit` 100/hour per IP | Consider per-IP + per-file caps; add referer/CSRF protection on download |
| Password | bcrypt cost 8–10 | Fine; consider cost 12 for future |
| Admin client | `getSupabaseAdmin()` used server-side with service role | Make sure it is never imported into client components |
| Cron cleanup | Deletes stale/unconfirmed files | Good — keep it scheduled; add quarantine for "infected" scan status |

Add **Cloudflare R2 CORS** `ExposeHeaders: ["ETag"]` for multipart (already expected in code) and restrict the
CORS `AllowedMethods` to `GET, PUT, POST, DELETE, HEAD`.

## 5. Performance Optimizations

- **Avoid `Promise.all` of many presigned signings** — use lazy part-URL generation (Issue A3/B3).
- **Cache `S3Client`** across calls (it is a singleton in `r2.ts` — good). Keep credentials refreshing automatically.
- **Un-limit check ordering**: in `initiate`/`presigned` you run `apiLimit` then upload limit then DB insert then
  signing. If you're going to reject for quota, reject early (you already do) — fine.
- **Reduce database round-trips**: the per-file collection link is an extra round trip per file; batch it.
- **Compression**: JSZip uses DEFLATE level 6 — fine; consider `STORE` for already-compressed folders to save CPU.
- **Frontend bundle**: many lucide icons are imported; rely on tree-shaking (fine with `lucide-react`).
- **Images/video previews**: `FilePreview` likely uses object URLs — ensure they are revoked to avoid memory leaks
  in long sessions.

## 6. Reliability & Robustness

- **Upload cancellation** is not implemented (only clear-all). Add a per-file Cancel that aborts the multipart
  session (you already have `/api/upload/multipart/abort`).
- **Retry policy**: implement exponential backoff with **jitter** and higher max attempts for idle/network errors;
  do not retry on 4xx (rate limit / validation) — those should surface immediately.
- **Idempotency**: make `complete` idempotent (guard against double-complete).
- **Global error boundary** and sentry-style logging for API routes.
- **Cron cleanup** already removes stale unconfirmed files — verify it runs on schedule in production.

## 7. UX & Feature Suggestions

1. **Show per-file progress + status with clear error reasons** (currently just "failed").
2. **Drag-and-drop folder + multiple selection** already works; consider a "queue" view with pause/resume.
3. **Session persist across reload** — shows a resumed upload (ties to B4).
4. **Large-file warning**: when a file > 2 GB is selected, warn about time/connection.
5. **Copy link / share modal** exists (`ShareCard`) — add QR export (already includes `qrcode.react`).
6. **Expiry defaults**: guests are forced to 7d max (good). Surface that clearly in UI.
7. **Command palette / keyboard shortcuts** optional.
8. **Add a download progress + "resume" for downloads** via range requests for large files.
9. **Accessibility**: ensure `aria-label`s on icon-only buttons; focus traps in dialogs.

## 10. Suggested Priority Order

1. Fix rate-limit model + messaging (Issue A) — *low effort, fixes multi-file failures*.
2. Lazy part-URL generation + adaptive concurrency + resumability (Issue B) — *medium effort, fixes 5 GB*.
3. Increase/extend download URL lifetime or stream (Issue B5).
4. Add storage quotas + magic-byte checks (Security).
5. Add tests + CI.
6. UX polish (per-file status, pause/resume, large-file warnings).
